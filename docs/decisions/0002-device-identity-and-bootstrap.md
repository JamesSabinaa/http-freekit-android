# Device identity and native trust bootstrap

Status: foundation implementation and tests in progress. No production wire integration, engine selection, or protocol freeze is implied.

`core-security` isolates Android Keystore operations from the preview interface. Each computer receives its own nonexportable P-256 signing key under an app-private alias derived from its opaque desktop ID. Creation must reject an existing key; loading a missing key returns a missing state and does not silently generate a replacement. A process-wide lock serializes create/load/delete across store instances, and an instrumentation regression checks concurrent creation. The app currently uses one process; supporting multiple processes would require an atomic registry/unique-alias design rather than relying on this lock. Forget removes that computer's key. Keys are restricted to SHA-256 signing/verification and are not exported, backed up, or assumed to be hardware-backed. Call Keystore operations off the UI thread. Platform behavior still needs device execution.

Enrollment uses a PKCS#10 request encoding the public key and a SHA256withECDSA proof of possession. Bouncy Castle 1.86 supplies ASN.1 structures; Java/Android Signature performs signing, so the private key stays in Android Keystore. No global security provider is changed. The full Bouncy Castle PKIX dependency was removed after lint found an unrelated trust-all helper in that library; only the provider/ASN.1 artifact is required. Its licence is retained in the repository and Android packaging merges licence resources instead of removing them.

The [Android Keystore guidance](https://developer.android.com/privacy-and-security/keystore) describes nonexportable key use and replacement of generated certificates by enrolled client chains. Client-certificate installation, chain validation, renewal, and credential persistence are not implemented by this checkpoint and remain required before authenticated Android-to-Node transport is claimed.

The initial custom pin-checking X509TrustManager was replaced with `GatewayTrust`: it validates a public self-signed leaf certificate against the configured SPKI pin, validates expiry and server/signing purpose, and builds an in-memory platform TrustManagerFactory with that sole gateway anchor. Normal TLS hostname checks remain enabled. Reconstruct trust on each connection/reconnect to recheck anchor expiry; callers must not reuse it indefinitely or install it in a global TLS context. Active-session expiry and certificate renewal policies remain contract gates.

The pin alone does not supply the certificate needed by this platform bootstrap. [Draft revision 0.2](../protocol.md) therefore adds optional public `gatewayCertificateDer` material to invitation parsing and requires newly generated desktop invitations to provide it. Existing pin-only draft invitations remain reviewable but are not sufficient for native enrollment. The desktop design owner was informed before this change and confirmed no production gateway depends on the previous draft. The certificate is bounded, validated, and distinct from the interception CA and all private keys.

Host tests cover PKCS#10 key binding, signature verification with JCA, mismatched signing keys, non-EC rejection, pin/expiry rejection, issuer-versus-leaf confusion, scoped platform trust, hostname rejection, and unchanged global SSL context. Instrumentation tests exercise creation/reopen/sign/CSR/delete and replacement rejection against the real Android Keystore; compiling that APK does not prove those tests pass on a device.

Native research now includes a [Linux packet-to-stream harness](../../tools/engine-spike/README.md) against the pinned Hev/lwIP engine. The Windows environment has no usable WSL virtualization or attached Android device. An x86 diagnostic emulator terminated without becoming usable, and automatic approval review rejected the ARM64 emulator command with only `blocked by policy`. Device and native Linux runtime results must be recorded separately after actual execution.

Local validation: ten core-protocol tests and six core-security host tests passed; the security Android instrumentation APK compiled; security lint reported no issues. All three synthetic host packet-driver/adapter checks passed, including prefix-gated uploads/downloads and write EOF before the reply. Python and PowerShell syntax checks and local Markdown links passed. Three Keystore instrumentation tests are compiled but unrun.

Hosted native evidence: [native-engine job 120858245928](https://github.com/JamesSabinaa/http-freekit-android/actions/runs/40089210986/job/120858245928) passed at Android commit `ac0881c8cf72c7006746cfe3dcd61d23e28e96a3` on Ubuntu 24.04. The pinned candidate reconstructed IPv4 and IPv6 TCP into the controlled SOCKS/explicit-proxy adapter for HTTP and opaque CONNECT streams. Each of four cases transferred 16,421 upload bytes and 32,787 response bytes, with prefix gates, write EOF before response, packet checksum validation, byte equality, and clean engine shutdown. Each response SHA-256 was `62a22a63bb850ba7b263fccff99e868133570394d36d6ee16fd32e9d7c1a4601`. These are real native-library results with synthetic packets, not Android TUN/routing, TLS, or actual desktop integration. The overall first workflow failed separately because Android SDK tools were missing from that runner; native and documentation jobs passed. SDK bootstrap is being corrected before claiming the whole workflow is green.

Desktop counterpart: `d5732519039c4c831c38813871fd291e047245a7` adds five controlled explicit-proxy byte-stream cases and gateway boundary analysis; `cad06c0cb1300e9b5e7e26201d1962cfc5e6d62c` selects interception certificates using validated SNI while retaining original CONNECT egress. The desktop proxy/Android/test-layout regression run passed 461 tests across 88 files on Node 26.7.0. This resolves downstream certificate selection only. H1 Host/upstream TLS and H2 authority semantics, actual destination policy, trusted device context, and rule/pool isolation remain gates in the desktop handoff. No companion gateway or paired Android/desktop capture run is claimed.

Review limits: `GatewayTrust.forCertificate` currently returns a reusable raw platform manager; production transport must enforce fresh validity checks for each connection and active-session expiry rather than rely only on a caller convention. An unpinned child certificate signed by a pinned non-CA leaf must also be rejected on Android. The host bootstrap tests do not establish these Android/runtime invariants. The security module is not wired into the app's mock connection flow.

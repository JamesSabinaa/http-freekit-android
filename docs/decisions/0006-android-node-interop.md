# Android Keystore to Node research proof

Status: isolated foundation instrumentation and loopback peer. Host fixture checks and Android compilation are separate from Android execution. This checkpoint adds no production enrollment endpoint, persisted credential, VPN, proxy delivery, desktop management access, or protocol freeze.

The research-only `:transport-interop` library lives under `tools/transport-spike/android`. Its main manifest is empty; only its instrumentation APK has INTERNET permission. It depends on public `core-security` APIs in test code. Ordinary Keystore instrumentation remains independent of Node. The research task requires a live peer and fails if arguments, connectivity, or any of its four cases are absent; it has no successful skip path.

## Reproduction

Host prerequisites are JDK 17, the repository's pinned Android SDK/build tools, Node 22 or later, OpenSSL 3, and an explicitly selected online API 26+ ADB device. OpenSSL 4 is intentionally outside this fixture's checked version range. If several installations exist, use `OPENSSL_BIN` or the driver's `--openssl PATH` option. No global provider, trust store, or device proxy setting changes are made.

From the repository root:

```sh
npm --prefix tools/transport-spike ci --ignore-scripts --no-fund
node --test tools/transport-spike/android-peer.test.mjs
node --test tools/transport-spike/instrumentation-results.test.mjs
./gradlew :transport-interop:assembleDebugAndroidTest :transport-interop:lintDebug
node tools/transport-spike/run-android-interop.mjs --serial emulator-5554
```

The driver supports `--adb PATH` and `--openssl PATH`. It uses `ANDROID_HOME/platform-tools/adb` when available and the root Gradle wrapper with a 15-minute build deadline. It first builds `:transport-interop:assembleDebugAndroidTest`, verifies the expected test application ID/output metadata, installs that test APK, and verifies runner registration. Only then does it start the peer and allocate reverse mappings. It invokes `adb shell am instrument -w -r` directly with the four public fixture arguments and exact research class, with a three-minute instrumentation deadline. [Android's command-line testing guide](https://developer.android.com/studio/test/command-line) documents this explicit build/install/instrument sequence. The driver is the runtime entry point; ordinary AGP connected execution is not used by it.

The peer starts two ephemeral TLS listeners on host loopback. The driver allocates two `adb reverse --no-rebind tcp:0 tcp:PORT` mappings and supplies only the public gateway certificate/pin and mapped enrollment/WSS ports as instrumentation arguments. Certificate authority and server private keys are synthetic, generated for that run under a verified temporary-directory prefix, with private file modes where supported. They never enter the repository or Android process. The Android client private key never enters the host or Node process. On success or failure the driver stops/uninstalls only its research test package, removes only its own reverse mappings, closes the peer's sockets/listeners, and deletes its temporary directory. Cancellation shares the same cleanup promise and waits for in-progress peer startup; no early process exit bypasses pending cleanup. It never removes all device mappings or touches the production app. Cleanup errors fail the command and its report.

## Bounded fixture protocol

This protocol is deliberately separate from the [companion draft](../protocol.md). It is an automatically issuing, loopback research fixture, without invitation approval or replay protection suitable for production.

- Bootstrap HTTPS accepts only `POST /research/enroll` with `application/pkcs10`, exact Content-Length 1–4096 bytes, no transfer encoding, and at most 8 KiB of request headers. Other paths return 404. Issuance is serialized, limited to eight successful requests per run, with a five-second idle limit and ten-second request deadline. Each listener permits at most 16 connections.
- A strict bounded DER envelope reader requires PKCS#10 v0, a bounded subject, empty attributes, canonical P-256 SPKI, and SHA256withECDSA with absent parameters. Node verifies the signature over the exact CertificationRequestInfo encoding before issuance. Altered signatures, trailing material, oversize bodies, malformed encoding, and other curves fail. The profile follows [RFC 2986](https://www.rfc-editor.org/rfc/rfc2986); Node uses its [public key and signature APIs](https://nodejs.org/docs/latest-v22.x/api/crypto.html).
- OpenSSL issues only a non-CA leaf with digitalSignature and clientAuth-only EKU, signed by an ephemeral path-length-zero enrollment CA. CSR extensions are never copied. The issued public key and CA signature are checked again before responding. [OpenSSL x509](https://docs.openssl.org/3.0/man1/openssl-x509/) documents `-req`, explicit extension files, and `-copy_extensions none`.
- Success is a binary envelope of at most 8201 bytes: version byte 1, big-endian unsigned 32-bit CA DER length and CA DER, then equivalent leaf length and DER. Each certificate is at most 4096 bytes. Android bounds lengths before allocation, reparses canonical DER, rejects trailing bytes, and validates/binds the credential through `DeviceIdentity`.
- A second TLS listener requires a verified client certificate against that ephemeral CA. Before `/research/echo` upgrades, Node also compares the peer SPKI against a successfully issued key from this run and rejects browser Origin. Binary WebSockets have a 64 KiB maximum payload and compression disabled. This peer echoes only its received research bytes; it cannot select a forwarding destination. [Node TLS](https://nodejs.org/api/tls.html#tlscreateserveroptions-secureconnectionlistener) documents mandatory client authentication.

Android uses `GatewayTlsConnectionFactory` for both bootstrap HTTPS and authenticated WSS, keeping dial loopback separate from the logical gateway name. The [scoped certificate manager](0004-enrolled-client-credentials.md) supplies the original nonexportable signing handle to the factory. The small instrumentation-only [RFC 6455](https://www.rfc-editor.org/rfc/rfc6455) client validates the HTTP upgrade and accept hash, masks outgoing frames, bounds incoming lengths before allocation, exchanges one exact 64 KiB binary payload, and closes. Each application I/O operation has five-second read and ten-second overall budgets; factory connection/handshake budgets are five seconds each. This deliberately limited client is not production streaming/framing code.

## Evidence boundary

Two host Node tests cover CSR proof failures and actual software-key issuance/mTLS/WSS echo, absent-client rejection, and temporary-directory cleanup. They exercise the fixture; they do not establish Android Keystore interoperability.

`com.httpfreekit.interop.AndroidNodeInteropTest` contains exactly four instrumentation cases:

- `nonexportableIdentityEnrollsAndEchoes64KiB`: create a real Keystore key, reject its altered CSR, enroll the valid CSR, validate/bind the issued chain, exchange 64 KiB through the public TLS factory, assert the same unexportable key handle and unchanged original Keystore certificates, then delete only that test identity.
- `wrongPinIsRejected`: establish peer reachability using the correct pin, then reject a different pin.
- `wrongHostnameIsRejected`: establish peer reachability, then reject an incorrect logical server name.
- `missingClientCertificateIsRejected`: establish bootstrap reachability, then require mTLS rejection, including application I/O to observe a TLS 1.3 alert that can arrive after the client's handshake call returns. Read timeouts and initial connection failures do not count as rejection evidence.

XML is under `tools/transport-spike/android/build/outputs/androidTest-results/connected/debug`; HTML is under `tools/transport-spike/android/build/reports/androidTests/connected/debug`. The driver clears only those fixed generated report directories before a run and writes fresh `TEST-android-node-research.xml` plus `index.html`. A strict bounded parser requires all four exact start/end pairs and the final instrumentation success result. Unexpected/duplicate identities, missing cases, failed statuses, skipped/assumption-failed tests, shortMsg/crash/aborted output, missing/duplicate terminal results, output-limit violations, and nonzero/timeout ADB execution fail the run. The reports always include four expected testcase entries; a never-started or unfinished case is an explicit error, never a claimed execution. Properties `actualStarted` and `actualCompleted` retain the actual counts. A run-level failure after four completed assertions still produces a report error.

Instrumentation stdout/stderr capture has a combined 256 KiB limit and is never printed or retained verbatim. Failure diagnostics keep only static failure categories, exception class names, and at most 32 allowed research/platform stack frames; exception messages, arbitrary paths, payload lines, and argument dumps are omitted. Reports do not contain full logcat, private keys, raw peer logs, or traffic bodies. Twenty-two host parser/diagnostic tests exercise successful pairing, multiline diagnostics/sanitization, empty failures, crashes, missing/duplicate cases, skip/assumption results, terminal failures, output caps, ADB failure/timeout handling, known stderr categories, exact exit/signal values, public version extraction, and private server-log boundaries. These tests establish diagnostic behavior, not Android execution. Hosted execution and its Android versions/commit pair must be recorded independently; compilation is not runtime evidence. [AOSP adb documentation](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/user/adb.1.md) describes ephemeral reverse ports and removal of specific mappings.

The parser's start/completion/failure/skip codes follow [AndroidX InstrumentationResultPrinter](https://github.com/android/android-test/blob/main/runner/android_junit_runner/java/androidx/test/internal/runner/listener/InstrumentationResultPrinter.java). After instrumentation the driver also checks that both owned device/host port pairs still exist; loss is an explicit run error without attributing its cause to a particular component.

The first hosted transport run (`40094676455`) produced one empty failed testcase on each API and no results for the other three cases. Both reverse listeners were absent by cleanup. That establishes neither the instrumentation failure cause nor which component removed mappings. Moving build/install before peer startup and using explicit instrumentation improves run control and diagnostics; it is not a claim that the underlying failure is fixed. The four TLS/identity assertions and production security classes are unchanged by this diagnostic follow-up.

The explicit-driver run `40096496418` at `b55526f` also failed on both APIs: exactly one start and zero completions, with no terminal instrumentation result. The ADB child failed and the subsequent reverse query was unavailable before workflow emulator cleanup. No Java/TLS assertion cause was reported. This establishes a channel failure observation, not whether the ADB client/server, emulator, or instrumentation caused it.

The next diagnostic checkpoint retains at most 16 KiB plus a truncation marker of ADB stderr inside the existing combined capture budget. It converts that text into fixed categories such as channel closed, missing/offline/unauthorized device, protocol fault, connection reset/refused, daemon startup/unreachable/version mismatch, and missing reverse listener; unknown text is only `adb_stderr_unclassified`. Raw stderr is never stored or printed. Reports include the actual child exit code or signal, without substituting a fabricated exit code after a timeout. Signal values and spawn errors are allowlisted. The driver also records public numeric client/build/daemon versions while omitting installation/server paths.

After instrumentation, bounded selected-device `get-state` and reverse-list probes record their own exit code, signal, and stderr categories. Device state is one of a fixed set; mapping contents are checked but never retained. These fields appear only as safe XML properties/HTML diagnostics and the same safe console summary. Standard ADB probes may start a daemon if none is running; they cannot establish that a previous daemon survived. F's separate workflow diagnostics distinguish emulator-launcher liveness after the driver exits. No retry, protocol relaxation, or TLS/test assertion change is introduced here; a fresh hosted execution is still required to establish the cause.

The private server-log diagnostic reads only the explicit `ANDROID_ADB_LOG_PATH` prepared by the runtime workflow before its first ADB call. There is no discovery or fallback to the shared default log. The configured file must already exist, be a regular non-symlink file, and on Unix be private and owned by the current user. Immediately before instrumentation the driver records an opaque file identity/size baseline and whether its last byte is a newline. Immediately after the child ends, before any recovery probe, it reads at most the first 64 KiB of appended bytes from the same file. Replacement/rotation, size shrink, changed identity, missing/inaccessible files, and partial boundary lines produce fixed status information without classifying stale or replacement bytes. Each baseline is single-use.

Only three verified literal markers are retained: `kill-server process callchain` produces `adb_callchain_positive_marker`; `failed to get kill-server process callchain` produces only `adb_callchain_capture_failed_marker`; and `adb server killed by remote request` produces `adb_remote_kill_request_marker`. A failed callchain capture is not positive attribution. Caller formatting is not established, so process names, command lines, arguments, serials, and paths are never extracted. At most 16 observed basename/line tokens from a small public AOSP `.cpp` allowlist may appear as source locations; these tokens are not caller attribution or a crash finding. The raw log and its explicit path never enter reports or console output. The cause remains unknown when no marker is observed; limits or missing logs reduce evidence further. The [37.0.1 release notes](https://developer.android.com/tools/releases/platform-tools#37-0-1) describe Linux kill-server blame, but do not establish its caller-chain grammar.

Seven additional server-log tests cover stale baselines, distinct positive/failed/remote-request markers, rotation/size shrink, the 64 KiB limit, partial lines, source allowlisting, single use, and canary exclusion. They create only synthetic private temporary logs and delete them after each case. This diagnostic does not change ADB/tool versions, TLS, enrollment, the four instrumentation assertions, or their pass/failure gate; no new runtime outcome is inferred from it.

Remaining gates include actual API 26/37 execution, physical hardware-backed key behavior, credential approval/persistence/renewal/revocation, active-session policies, cancellation/backpressure and sustained streaming, packet forwarding, real desktop proxy integration, USB capture with phone radios disabled, and LAN/WAN acceptance. This proof does not freeze the production CSR/certificate policy or any companion route.

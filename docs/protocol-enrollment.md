# Draft enrollment contract 0.4

Status: normative for the A21 foundation implementations and shared fixtures only. Protocol v1 is not frozen. This adds the missing enrollment grammar; the control/stream appendix remains revision 0.3. A21 supplies codecs, proof bytes, a headless challenge coordinator and a durable reference authority. A22 has [verified research evidence](validation.md#android-enrollment-https-runtime) for HTTPS/Android Keystore/approval/save/reopen, adversarial proofs/TLS/cancellation and active-session revocation/credential expiry. Renewal/rotation decisions, capture policy, production integration and physical-network gates remain open.

## Trust and encoding

All setup requests require the existing scoped gateway TLS pin, logical-name and certificate-validity checks. New native enrollment requires the invitation's public gateway certificate; older pin-only invitations remain reviewable but cannot start this path. Private device and authority keys are never wire fields. Setup credentials do not authorize streams or management operations.

Bodies are at most 16384 UTF-8 bytes. Reject malformed UTF-8, BOM, non-object roots, invalid JSON, unpaired UTF-16 surrogates after escape decoding, decoded duplicate member names, depth above 3, more than 16 members in an object or more than 16 array elements. The root object has depth 1; each nested object or array adds 1. Every numeric token must be a canonical nonnegative integer of at most ten decimal digits. After structural validation, require a numeric protocolVersion in 1..2147483647; values other than 1 yield unsupported_version before type-specific schema validation. For version 1 require exactly the listed fields and correct channel/type. Size failure is message_too_large; other structural/schema failures are invalid_message. Semantic service authorization follows successful decoding. Unknown fields are not optional.

Use canonical unpadded base64url: decode within its stated bound and require re-encoding to equal the supplied string. IDs desktopId and invitationId match [A-Za-z0-9_-]{1,128}. Enrollment IDs are enr_ plus 43 canonical base64url characters encoding 32 random bytes; challenge IDs use ech_ and device IDs use dev_ with the same form. Hashes, invitation secrets and nonces encode exactly 32 bytes. DER CSRs/certificates encode 1..4096 bytes. Timestamps are exact valid UTC YYYY-MM-DDTHH:mm:ssZ in years 2000..2099, without fractional seconds or offsets.

Device names contain 1..128 UTF-8 bytes of well-formed Unicode, without U+0000..U+001F, U+007F..U+009F, U+2028/U+2029, U+202A..U+202E, U+2066..U+2069 or U+FEFF, and without leading/trailing ASCII space U+0020. They are untrusted display text, not identity. Capabilities are 1..16 distinct strings matching [a-z][a-z0-9-]{0,31}; canonical encoders sort them by ASCII order. Codecs preserve no arbitrary error detail. DTO default string/inspection/JSON diagnostic representations redact material; explicit wire encoding/material access is separate.

Canonical encoders use compact JSON, the field order below, raw UTF-8 for allowed non-ASCII characters, and only necessary quote/backslash escapes. Decoders accept insignificant JSON whitespace and ordinary valid escapes. They validate byte/resource limits before payload-dependent allocation.

Wire certificates and CSRs are opaque bounded DER bytes at the codec layer; their semantic/cryptographic profiles are checked by the authority or existing credential binder. Codec acceptance alone is not authorization.

## Exact messages

Each list below includes protocolVersion first and type second. Those common fields are not repeated in the remaining-fields column. All values are strings unless specified otherwise.

| Channel | type | Remaining fields, in canonical order |
| --- | --- | --- |
| pair request | pair | desktopId, invitationId, invitationSecret, csrDer, deviceName, capabilities (array) |
| challenge request | pair_challenge | desktopId, invitationId, enrollmentId, purpose |
| status request | pair_status | desktopId, invitationId, enrollmentId, challengeId, signature |
| cancel request | pair_cancel | desktopId, invitationId, enrollmentId, challengeId, signature |
| pair response | pair_registered | desktopId, invitationId, enrollmentId, deviceSpkiSha256, reservationExpiresAt, resultExpiresAt |
| challenge response | pair_challenge | desktopId, gatewaySpkiSha256, invitationId, enrollmentId, challengeId, deviceSpkiSha256, purpose, nonce, expiresAt |
| status response | pair_pending | desktopId, enrollmentId, reservationExpiresAt, retryAfterMillis (integer, exactly 1000) |
| status response | pair_approved | desktopId, enrollmentId, deviceId, clientCertificateDer, enrollmentAuthorityDer, interceptionCaCertificateSha256, capabilities (array), credentialExpiresAt, resultExpiresAt |
| status or cancel response | pair_ended | desktopId, enrollmentId, code |
| any response | pair_error | code |

purpose is status or cancel. signature is canonical DER ECDSA (r,s), base64url, 8..72 decoded bytes. Its sequence and positive INTEGERs use minimal DER lengths/encoding, scalars are in 1..n-1 for P-256, and no trailing bytes are allowed. Both high-S and low-S valid signatures are permitted; replay identity is the challenge, not signature bytes. Client certificates are single leaves directly issued by the separately supplied enrollment authority, not a chain inferred from the interception CA. interceptionCaCertificateSha256 hashes the complete canonical interception CA DER, not its SPKI.

pair_ended codes: pairing_rejected, pairing_cancelled, invitation_expired, device_revoked, credential_expired, result_expired. pair_error codes: invalid_message, message_too_large, unsupported_version, unsupported_capability, authentication_failed, invitation_expired, invitation_used, pairing_limit, pairing_unavailable. Invalid invitation/secret/key-bound credentials use authentication_failed without field/path/provider detail. A syntactically valid error response is accepted on every response channel; an unrelated success type is invalid_message.

A22 transport maps pair to POST /companion/v1/pair, challenge and status to POST /companion/v1/pair/status, and cancellation to POST /companion/v1/pair/cancel. Require bounded application/json bodies with exact Content-Length, no transfer coding, query, browser Origin, Cookie or generic Authorization, and duplicate-critical-header rejection. These are the only setup routes; they cannot approve a request or open traffic. HTTP transport itself is outside A21.

## Signed proof bytes and client checks

The client reconstructs these bytes from typed validated fields and its saved setup context; it never signs arbitrary bytes supplied by the server. Before signing, require exact desktop, gateway pin, invitation, enrollment, current device-SPKI and purpose matches between context and challenge. Derive method/path solely from that matched purpose. Neither a display name nor a dial address establishes identity. Only an explicitly requested cancel operation may use purpose cancel.

For explicit review, the comparison fingerprint is SHA-256 over ASCII HTTP FreeKit pairing comparison v1 followed by NUL, then the raw 32-byte gateway SPKI hash and 32-byte device SPKI hash. Display its 64 lowercase hex digits as eight groups of eight separated by hyphens. This public fingerprint does not approve a request.

Start with the ASCII bytes HTTP FreeKit enrollment proof v1 followed by one NUL byte. Append, in this order, each string as a two-byte unsigned big-endian UTF-8 byte length followed by its bytes:

1. purpose (status or cancel)
2. POST
3. /companion/v1/pair/status for status, or /companion/v1/pair/cancel for cancel
4. desktopId
5. invitationId
6. enrollmentId
7. challengeId
8. expiresAt from this challenge

Then append exactly 32 raw bytes each: gatewaySpkiSha256, deviceSpkiSha256, nonce. The complete payload must be at most 1024 bytes. Sign with the existing P-256 device key and SHA256withECDSA. The server reconstructs the identical payload using its immutable challenge/registry binding and verifies the signature using the reserved SPKI. Client time does not authorize a challenge; the server's ten-second monotonic lifetime does. The signed expiry string is the immutable informational UTC value issued with that challenge.

## CSR and public certificate profile

New reservation validates a complete bounded PKCS#10 profile, not just a signature over opaque subject bytes. Require canonical DER; version 0; exact subject CN=HTTP FreeKit device encoded as one UTF8String commonName RDN; canonical uncompressed P-256 SubjectPublicKeyInfo; empty attributes; ecdsa-with-SHA256 without parameters; canonical DER ECDSA proof verified by the established provider. No requested extension or subject supplied by a CSR is copied into issued certificates. The separate deviceName is display-only. Distinct valid ECDSA signatures over the same request therefore resume by canonical SPKI, never raw CSR hash. The older research verifyRequest helper alone is insufficient validation of the subject.

The dedicated authority is a self-signed P-256/SHA-256 CA with critical CA:TRUE,pathlen:0 and critical keyCertSign/cRLSign-only usage. Authority EKU is absent or clientAuth-only. The direct client leaf is P-256/SHA-256, critical CA:FALSE, critical digitalSignature-only usage and clientAuth-only EKU, with the same fixed device subject. EKU may be critical or noncritical. It has a unique positive issuer serial, an exact matching SPKI, canonical DER, an issuer Name matching the authority subject, a valid authority signature and a current validity interval contained by the authority. Reject unknown critical extensions and duplicate extension OIDs. Well-formed bounded unknown noncritical extensions are permitted and never treated as authorization instructions; SKI/AKI may be retained. Established cryptographic providers verify points/signatures/certificates; bounded DER profile inspection is not a replacement for cryptography. Arbitrary CSR extensions are not authority instructions.

A21 issuer jobs persist exact expected serial, SPKI, subject, capabilities and not-before/not-after parameters before signing. Let T be the issue UTC rounded down to seconds. notBefore is max(authority.notBefore, T - 300 seconds); notAfter is min(authority.notAfter, T + configured lifetime). Require notAfter >= T + 60 seconds, otherwise pairing_unavailable. The configured future lifetime is at most 90 days; the interval may additionally contain its five-minute backdate. In A21 credentialExpiresAt is exactly the leaf notAfter (already contained by the authority), with no inferred gateway/interception expiry. Production gateway/session lifetime composition and renewal remain A22/later gates. A candidate with any wrong key, issuer, purpose, dates, serial or profile is never published. The headless store owns public records, not signing keys or subprocesses; its trusted caller must join actual signing work before resolving/releasing a job handle.

## Reservation, decisions and recovery

Invitations use 32 random secret bytes; persist only their SHA-256 verifier and immutable identity/deadline. Default invitation lifetime is five minutes. A reservation's deadline is that original invitation expiry; its result deadline is exactly one hour after reservation creation, both rounded down to UTC seconds. Neither retry, challenge issuance, decision, restart nor lost response extends either deadline. At now >= a deadline it has expired.

After wire validation, authenticate invitation ID/secret with bounded lookup and constant-time verifier comparison before expensive CSR work. Verify the new CSR/profile and canonical key before reserving. An unknown ID, wrong secret, wrong desktop or invalid proof fails without reservation. For an unclaimed live invitation, reserve atomically for that key, the first review snapshot and a fresh enrollment ID. The granted capabilities are exactly the sorted complete requested-set intersection with configured supported capabilities; an empty intersection is unsupported_capability. Persist this grant with the review snapshot and do not select a different subset during approval. Repeated requests with the same key and unchanged name/capability set return the identical pair_registered fields even if the valid CSR signature bytes differ. They never replace the original reviewed CSR/metadata. A different key cannot steal or resume the invitation. Changed review metadata on a same-key retry is invalid_message.

A matching same-key/secret CSR retry may recover that existing public registration record until its fixed result deadline, including after invitation consumption/expiry. This grants no status read, approval or traffic; the subsequent proof is still required. It cannot create a new reservation. Different-key/unknown-secret attempts remain denied. A second live enrollment/active grant for the same SPKI is denied; terminal grant history does not authorize a new one. Re-enrollment/renewal UX remains a later gate; no old invitation revives a terminal enrollment.

States are pending, issuing, approved, rejected, cancelled, expired or revoked. Public status for pending/issuing is pair_pending. Only a trusted local operator can approve or reject. Approval records durable explicit intent, then claims an issuer job with a fresh signing generation/token and a never-reused issuer serial allocated durably. Signing happens outside the DB transaction while the owner lease is retained. A new owner may reclaim an unfinished approved intent before its original reservation deadline; it must allocate a new generation/token/serial so a previous orphan candidate is never reusable. Approval after deadline is refused. Duplicate approve after committed approval returns the stored result without another issuance.

Publication is one conditional transaction: recheck owner health, current clock, exact invitation/key/review binding, decision, reservation deadline, generation/token, and validated candidate; then store the exact approved result, current credential/registry entry and consumed invitation together. Nothing authorizes a signed but unpublished candidate. A crash before commit leaves no active credential; a crash after commit but before response returns the identical stored result to a later fresh status proof. No response-delivery acknowledgement rolls publication back. The approved result is immutable; current status/revocation can suppress its return.

Reject/cancel/revoke while issuing invalidates the job generation. If publication already won, an explicit rejection or cancellation of this enrollment revokes its exact newly published grant atomically; it cannot affect a later enrollment sharing the key. The first terminal decision wins and cannot be approved again. Cancellation requires a fresh cancel-purpose proof; status-purpose signatures cannot mutate state. A valid cancel is idempotent and returns the current pair_ended state, with pairing_cancelled when cancellation won. Local revoke returns device_revoked on subsequent status. Expired pending/issuing reservations return invitation_expired. An expired active credential denies traffic and returns credential_expired. Status after the result deadline returns result_expired without certificate material; it does not extend or implicitly renew an otherwise active credential.

Authorization always checks the exact current leaf DER hash, SPKI, device/grant binding, active/revoked state, current validity and configured authority identity. A CA-valid certificate or matching SPKI alone is insufficient. Old/orphan/unknown/revoked leaves fail even when another leaf with the same key is current. A21 proves the headless authorization result; A22 supplies separate verified real WSS revocation and credential-expiry teardown evidence. Production integration remains gated.

## Challenges and clocks

A challenge request needs the exact registered desktop/invitation/enrollment tuple and a record within its result window, but cannot read status. Challenge IDs and nonces are fresh random 32-byte values. Bind the immutable key hash, gateway pin, context, purpose and expiry to the stored challenge. Permit at most two live challenges per enrollment and 32 per owner, with at most one issuance per enrollment per 1000 monotonic ms and one globally per 100 ms. Repeated/flooded requests cannot evict a live challenge or reset its ten-second deadline; return pairing_limit. Expired challenges release capacity. Outstanding challenges are deliberately memory-only and all become invalid on owner restart.

Keep consumed-ID tombstones until their original monotonic expiry so replay and collisions cannot reuse a still-live ID. At most 128 resident live/tombstone IDs are permitted; global issuance timing bounds this set, and reaching the cap is pairing_limit. Exhausted challenges continue to occupy their original active slot until expiry. Collision avoidance covers resident IDs; secure random freshness is required outside that window and across restarts. No challenge history is persisted or exported.

The informational challenge expiresAt is floor-to-UTC-second(issued UTC + 10000 ms). Its authoritative monotonic deadline is exactly issued monotonic time + 10000 ms. Random-ID collisions retry at most eight times and otherwise fail closed. CSR/proof verification shares an owner budget of at most 16 attempts in any rolling 1000 monotonic ms and at most four per invitation in that interval; unknown-secret requests do not reach CSR crypto. Rate rejection does not consume a challenge or extend a deadline.

Before crypto, check bounded canonical input, known challenge/context/purpose and monotonic lifetime. Invalid signatures do not consume or mutate enrollment state, but permit at most three verification attempts per challenge; an exhausted slot stays unusable until its original expiry. After a valid signature, recheck the same immutable challenge/binding and its lifetime, including verification time, then consume synchronously before current-state lookup/response, with no await/reentrancy gap. At most one concurrent/replayed submission succeeds. Response loss or storage failure never restores a consumed challenge. A client obtains another challenge to retry. Parent result expiry still prevents status material or cancellation authority beyond that deadline.

Successful challenge insertion alone advances issuance timestamps. An event exactly now - 1000 ms is outside a rolling crypto window and releases capacity. Charge a crypto attempt immediately before CSR/profile or signature verification, including attempts that fail; never refund it after a later deadline or publication failure. Unknown/expired/exhausted/mismatched challenges are rejected before shared crypto quota. A shared-quota refusal leaves the challenge's three-attempt count unchanged. A completed invalid signature increments that count; a completed valid signature is single-use even when response delivery or current-state lookup later fails.

### Service and state precedence

Apply the following gates in order; a failure does not continue to later gates.

| Operation | Ordered gates and exact outcomes |
| --- | --- |
| Every request | Decode size/structure/version/schema first. Then closed/unhealthy store or invalid clock yields pairing_unavailable before binding/credential checks. |
| Pair reservation | Wrong desktop, unknown invitation or wrong secret: authentication_failed. Unclaimed expired invitation: invitation_expired before CSR work. Claimed invitation past its result deadline: invitation_used. Then shared crypto quota, strict CSR proof (failure: authentication_failed), existing-key conflict (invitation_used), same-key changed review metadata (invalid_message), capability intersection (unsupported_capability), live-SPKI conflict (invitation_used), capacity and atomic fresh-clock/deadline recheck. |
| Challenge issuance | Unknown/mismatched desktop/invitation/enrollment or expired result window: authentication_failed. Then expire old nonce slots, enforce issuance/slot quotas, allocate a collision-free immutable challenge and update successful-issuance timestamps. No current enrollment status is returned here. |
| Proof submission | After store health, unknown/consumed/expired/exhausted challenge or context/purpose mismatch: authentication_failed. Then shared crypto quota. Invalid signature: authentication_failed and one failed attempt. A valid signature must pass the final exact-binding/monotonic-TTL check, then be consumed once before any status read or cancellation. |
| Valid proof crossing parent result deadline | Consume a still-live valid challenge, return pair_ended/result_expired for either purpose, and return no certificate or cancellation mutation. A new challenge after that deadline is not issued. |
| Current-state result | Unknown record: authentication_failed. First apply due reservation/credential expiry to a nonterminal state. If result deadline is elapsed, return result_expired regardless of revocation/credential/decision status. Otherwise a persisted terminal state wins; then pending/issuing returns pair_pending, approved returns its exact stored result. |

The terminal set is rejected, cancelled, expired and revoked. approved is deliberately nonterminal and revocable. Due expiry of pending/issuing becomes expired with invitation_expired; due expiry of approved becomes expired with credential_expired and an inactive exact grant. Once terminal, later decisions/computed expiry do not replace that reason. The result-window check changes only what can be delivered, not an otherwise active grant. cancel and reject recheck the result deadline in their own transaction and do not mutate after it; trusted local revoke can still revoke a grant after its setup-result window. All decisions first observe any already-due reservation/credential expiry.

Persistent deadlines use trusted UTC and survive restart as original absolute values. In-process deadline anchors also cap remaining lifetime using monotonic elapsed time, so a frozen wall clock cannot extend a live reservation. Every clock observation, including failed/rate-limited requests, advances in-memory UTC/monotonic high-water values. Business mutations and the owner bootstrap transaction persist the UTC high-water in the same commit; successful read-only now/auth/proof calls do not write it. Rollback restores the prior durable value, never an authorization grant. Reject backwards monotonic time and UTC below the current in-memory value or, on reopen, the durable value; latch unavailable until a healthy reopen. Do not reset a deadline to now plus its lifetime. After restart, monotonic anchors are re-established from remaining original UTC time and all challenges are gone. This does not claim detection of rollback within an unpersisted read-only interval or protection from an attacker controlling the host clock/storage across restarts.

## Durable reference store and bounds

Use one explicitly initialized local database and a separate openExisting path. Never initialize, migrate, regenerate keys or reset on missing/empty/corrupt/wrong-version/mismatched state. Bind metadata to the desktop ID, gateway pin, explicit enrollment authority/public identity and interception CA fingerprint. Prepared bound statements, strict tables, foreign keys, no extension loading, defensive mode and untrusted-schema denial are required. Read back all safety pragmas because unknown ones can be silently ignored.

The pinned Node 24.22.1 builtin SQLite API is a release candidate used for this isolated reference, not yet a production dependency selection. Use DELETE journaling, synchronous=EXTRA and EXCLUSIVE locking. Setting locking_mode alone is insufficient: acquire an exclusive bootstrap transaction, validate complete schema/metadata/integrity/FKs/business/certificate invariants, update the owner guard, commit and retain that connection before publishing authority access. A second owner/reader must fail with bounded busy handling. Release the DB last, after all trusted job/transport owners have actually finished; failed teardown retains ownership and denies new authorization. Never delete a hot journal as recovery. SQLite errors roll back the complete transaction, latch unavailable and expose only fixed errors; no cached enrolled-set fallback.

Reference caps: 64 invitation records, 128 enrollment records, 64 active credentials, 256 credential-history records, four in-process issuer jobs, and a 16 MiB database (4096-byte pages/4096 pages). Prune only safely expired/terminal delivery/history data, retaining active grant records and never reusing the durable issuer serial counter. Capacity exhaustion is explicit pairing_limit. Read back page size/count caps; use bounded static SQL, bound values, exact strict schema/CHECK limits and guarded length-before-BLOB reads. The pinned API has no sqlite3_limit interface: do not claim unknown PRAGMAs enforce value/SQL/depth/attachment limits. Install an authorizer denying attachment/detachment, extension loading and unauthorized schema operations; never expose arbitrary SQL. These caps do not claim total-process or filesystem memory bounds. Public records and verifier hashes are not encryption at rest. Require a local canonical private directory/regular non-symlink single-link DB; copied databases/keys, malicious same-user filesystem access and arbitrary network filesystems are outside this lock's guarantee.

## Trusted reference API

These module methods are internal foundation interfaces, not HTTP operations. Runtime clock input is a function returning safe integer utcMillis and nonnegative owner-relative monotonicMillis. Random generation defaults to crypto.randomBytes; deterministic substitutes are test-only. Metadata binds desktopId, gatewaySpkiSha256, enrollmentAuthorityDer, interceptionCaCertificateSha256, supportedCapabilities and an explicit credentialLifetimeSeconds in 60..7776000, default 3600 for the reference. Authority/gateway private keys are not store fields. Actual private-key provisioning and gateway lifetime composition remain A22 gates.

Store options are exactly directory, metadata, optional clock and optional randomBytes. Metadata DER/hash values use canonical base64url strings. All material snapshots expose an explicit material() copy with copied wire-shaped strings/arrays, redact default inspection/string/JSON representations, and retain no caller-owned mutable array. Fixed store errors carry only one pair_error code without provider/SQL/path causes. An unknown/failing authenticated lookup never becomes an empty allowlist or automatic initialization.

createInvitation material has exactly invitationId, invitationSecret and expiresAt. getBinding material has exactly desktopId, gatewaySpkiSha256, invitationId, enrollmentId, deviceSpkiDer, deviceSpkiSha256, reservationExpiresAt and resultExpiresAt, including for expired known records. Its optional fourth argument is {requireLiveResult:false}; true refuses authentication_failed at the store's UTC or monotonic result deadline. Its observedAt() method returns a copied clock observation from that exact check, separately from material(). The coordinator uses true and this observation for issuance, and false to reconstruct held proofs, so a frozen wall clock cannot extend the store's existing anchor. authorizeCertificate returns null for ordinary invalid, unknown, revoked or expired input. An allowed snapshot has exactly desktopId, deviceId, enrollmentId, clientCertificateSha256, deviceSpkiSha256 and credentialExpiresAt. Store/clock/corruption failures throw pairing_unavailable rather than an allow decision. Existing expired public credentials remain structurally valid on reopen: validate their profile/signature/binding without requiring current dates, then enforce current dates at publication, authorization and status. Expired history is never a reason to reset the database.

For Node, wire channels are pair_request, challenge_request, status_request, cancel_request, pair_response, challenge_response, status_response and cancel_response. decodeEnrollment(channel, bytes) returns either {ok:true,message} or {ok:false,code}; enrollmentMessage(channel, material) constructs a validated typed snapshot, and encodeEnrollment(message) returns fresh canonical bytes. material() is a copied wire-shaped object, with binary values represented as canonical base64url strings. enrollmentProofPayload(context, challenge) and enrollmentComparisonCode(gatewayPin, deviceHash) are the explicit proof/review builders. The exact context fields are desktopId, gatewaySpkiSha256, invitationId, enrollmentId, deviceSpkiSha256 and purpose. Builder/encoder misuse yields a fixed invalid_message error without input material. Kotlin mirrors these semantics with DraftEnrollment-prefixed typed classes and enums; fixture adapters do not depend on object layout.

| Store operation | Contract |
| --- | --- |
| createEnrollmentStore(options), openEnrollmentStore(options) | Explicit creation versus existing-state recovery; acquire/retain the owner lease before returning. |
| createInvitation() | Generate a fresh opaque invitation ID and 32-byte secret; return ID, secret and fixed UTC expiry to the trusted local caller only. |
| reserve(pair material) | Authenticate invite before crypto, charge shared crypto budget, validate CSR/profile, and atomically reserve/resume; return pair_registered material. |
| getBinding(desktopId, invitationId, enrollmentId, options) | Return copied immutable IDs, gateway pin, SPKI DER/hash and original deadlines for an exact known record; no status/result. Issuance explicitly requests requireLiveResult to enforce both clock anchors before issuing a challenge. |
| verifyProof(enrollmentId, payload, signature) | Charge the same crypto budget and verify using that immutable key; return a boolean, with no enrollment-state mutation. |
| beginApproval(enrollmentId) | Persist explicit local approval if pending, then claim a fresh job; resume persisted issuing intent only when no live local job owns it. Return a job or an already-approved immutable result. |
| publish(job, clientCertificateDer) | Validate and conditionally commit exact grant/consume/result together; settle that in-process job handle after its caller's signing work has finished. |
| abandon(job) | Invalidate and settle an owned job after actual caller cleanup; retain approved intent for a later fresh claim, without authorizing its candidate. |
| reject(enrollmentId), cancel(enrollmentId), revoke(enrollmentId) | Trusted state transitions with first-terminal precedence and exact-grant revocation; cancellation is exposed remotely only through the proof coordinator. |
| readResult(enrollmentId) | Read current expiry/decision/registry state and return pair_pending, pair_approved or pair_ended material. The caller must have consumed a valid purpose-bound proof for remote access. |
| authorizeCertificate(clientCertificateDer) | Headless current exact-leaf registry decision with copied device/deadline metadata; connection key-possession must still be established by mTLS in A22. |
| now() | Observe/validate the shared clock without extending an existing deadline. |
| close() | Deny further authorization, refuse to release the lease while local job handles remain, and close only after caller-owned work is actually joined. |

beginApproval allocates serials from a persisted strictly increasing safe-integer counter, never random reuse or rollback of an allocated serial after a committed job claim. Recovered attempts allocate another serial. Jobs contain copied expected SPKI, subject/profile, capabilities, exact validity, serial and opaque generation/token; old-owner or settled handles cannot publish. Approval results expose public certificate material only. The root coordinator owns its bounded challenge store and calls these synchronous primitives; no actual listener, issuer subprocess or app flow is hidden inside this API.

createEnrollmentAuthority({store,randomBytes}) constructs that headless coordinator; randomBytes is optional and defaults to the provider CSPRNG. request(channel,bytes) accepts only the four request channels and returns a validated EnrollmentMessage on the corresponding response channel, with fixed pair_error results for decoding/service failure. Synchronous reentry is refused before another proof can execute. close() denies further work and clears memory-only challenges; the creator retains the store and must join signing/transport owners before closing it. Coordinator shutdown does not silently release the database lease.

The exact beginApproval discriminator is {kind:job,job:JobSnapshot} or {kind:approved,result:ResultSnapshot}; values job and approved are strings. A due invitation expiry refuses approval with invitation_expired; other terminal/result-expired states refuse with invitation_used. Job material has exactly these fields: desktopId, invitationId, enrollmentId, deviceId, generation (integer 1..2147483647), token (32-byte base64url), serial (canonical positive decimal string in 1..9007199254740991), deviceSpkiDer (canonical base64url), deviceSpkiSha256, csrDer, capabilities (granted sorted array), notBefore, notAfter, subject (exact CN=HTTP FreeKit device), profile (exact p256-client-auth-v1). Allocate and persist deviceId once at first approval; recovered jobs keep it but take new generation/token/serial and date parameters. Duplicate committed approval returns the same public result.

publish is allowed only for an unsettled handle from this healthy owner instance. Invalid/stale/rejected/expired/CAS-losing candidates never publish and yield authentication_failed; after caller signing cleanup they settle that handle even when publication is refused. A SQLite failure instead latches pairing_unavailable. abandon remains permitted after closing/unavailable state for a handle issued by this owner, without a fresh clock check: invalidate its generation if storage is healthy, but always remove the joined local handle even if that cleanup write fails. It cannot authorize anything. Repeated abandon of an already-settled owned handle is a no-op; foreign/forged handles fail authentication_failed. close marks the instance closing before checking handles, denies all new work/publication, retains its DB lease if handles remain, and can be retried after actual work joins and abandon. This cleanup path must not be blocked by the unavailable latch.

A21 does not compact enrollment/credential history under a live challenge or issuer handle. Safe unused-invitation expiry may release invitation capacity; other full-history conditions fail explicitly until coordinated maintenance with no dependent owners. Removing an inactive history record can never authorize its certificate: authorization is an exact active allowlist, and serials are never reused. Production maintenance and key-renewal policy remain separate gates.
